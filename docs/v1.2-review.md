# v1.2 frontend and backend review

Reviewed October 7, 2026 against the requested feature list, using the current working tree, including uncommitted changes. This is a repository review, not verification of the deployed DigitalOcean app. Application code was not changed during this review.

**Verdict: v1.2 is partially scaffolded and not release-ready.** The new models, serializers and services are real, but the existing screens still use legacy records, important workflows are not wired, and core financial/inventory rules can be bypassed.

“Partial” means some implementation exists; it does not mean the whole feature is usable or safe. Model fields, comments, unused components and API-client wrappers do not count as completed user workflows.

## Release blockers, in priority order

### 1. Vendor listing and manual intake are broken — P1

`frontend/vendorops/src/routes/vendors/+page.server.ts:5` reads `auth_token`, while login and hooks use `vendorops_session` (`src/lib/server/auth.ts:3`). The loader returns `vendors`, but the page reads `leads`, `categories`, `sources` and `loadError`. The old create action is no longer exported, although AddVendorLeadModal still posts to `?/create`.

Reproduction: npm run check fails with seven errors on the vendor list page. A correctly logged-in user also cannot satisfy the loader's cookie lookup. Fix the cookie, data contract and create action together.

The new API client hardcodes localhost instead of using the existing private DJANGO_API_URL. Its filtered-list wrappers promise arrays but receive objects containing count/results. Fix these contracts before connecting more screens.

### 2. Team members can confirm unpaid bookings and bypass audits — P1

`backend/api/views_phase2.py:253` exposes generic Booking ModelViewSet create/update/delete to any authenticated user. `serializers_phase2.py:142` leaves status, market, invoice and booth writable. No payment check or admin override is enforced by this route.

Reproduction: a non-staff user created a confirmed booking against an unpaid invoice with HTTP 201; no booking-confirmed audit entry was created. Market and invoice CRUD also lack Admin versus Team Member boundaries.

Restrict sensitive writes to explicit, permission-checked service actions. Protect the Django admin paths too: current admin classes allow direct changes to financial/state records.

### 3. Payment recording is neither idempotent nor concurrency-safe — P1

`backend/api/services/payments.py:46` skips the overpayment guard when the balance is already zero. The service accepts repeated transaction references, has no idempotency key/constraint, reads stale invoice amounts, and does not lock the invoice. Atomic blocks alone do not prevent concurrent lost updates or duplicate receipts.

Reproduction: recording the same reference twice against a $10 invoice created two payments and amount_paid = $20. Full payment with a hold on a fresh profile failed with “Cannot transition from not_booked to confirmed”; hold creation never establishes the required reserved profile state.

The payment API requires an invoice field in the request body despite the invoice already being selected by the URL (`views_phase2.py:208`). A normal body containing amount/date/method returned HTTP 400. It validates one serializer then uses raw request data, and does not forward receipt uploads. Payment reversal deletes the payment, has no enforced role check/audit, and leaves profile/hold state inconsistent.

### 4. Capacity and hold rules are not enforced — P1

`backend/api/services/inventory.py:13` creates holds without checking capacity or locking stock. Reproduction: a capacity-one booth accepted two active holds. The displayed zero is clamped; it hides excess allocation rather than preventing it.

Availability counts only confirmed bookings and boolean-active holds (`models.py:377`). Preparing/attended bookings cease consuming capacity, and passed expiry timestamps still consume capacity until the boolean is updated. No scheduled job or management command invokes expire_holds. Confirmation does not reject expired holds or check full payment itself. Extensions/releases lack required permissions and audit entries.

The unique booking constraint only covers reserved/confirmed (`models.py:672`), permitting another booking when an earlier booking changes to preparing. No explicit admin override exists. There is no market-wide capacity enforcement or validation that invoice, variant and booking belong to the same market/vendor.

### 5. New invoice sending reports success without sending — P1

`backend/api/views_phase2.py:195` contains a TODO for email delivery. Send only writes sent_at and activity; it does not send email or transition the invoice/profile status. Resend, reminders, cancellation and overdue processing are absent.

Invoice creation uses generic CRUD rather than an invoice service: no automatic invoice number, calculated totals, validated line-item workflow, inventory hold or creation activity. Invoice number is read-only in the serializer but has no generation implementation. Generic PATCH permits direct financial/status changes without required audit.

The legacy approval endpoint still creates MarketWeekendBooking records when an invoice is sent (`backend/api/invoices.py:121`). Those legacy records are not synchronized with the new paid-only Booking model. Existing UI therefore still follows the old invoice-to-schedule behavior.

### 6. Dashboard and add-on inventory have runtime errors — P1

`backend/api/views_phase2.py:405` aggregates balance_due, which is a Python property, not a database field. Reproduction: authenticated dashboard GET raises FieldError.

`backend/api/models.py:411` queries invoice__payment_status although Invoice has status. Reproduction: computing inventory for a stocked add-on raises FieldError. Add-on hold quantities are not included in availability, zero inventory is treated as unlimited/unknown, and confirmation loses quantities by storing a plain many-to-many selection.

### 7. Canonical profile migration and intake integration are missing — P1

Manual and CSV intake still create only VendorLead (`views.py:22`, `applications.py:136`). No intake call, signal or data migration creates VendorProfile for these records. Migration 0011 creates tables but does not backfill existing vendors, invoices or bookings. Profile statuses therefore cannot be the single source of truth for the current screens.

The duplicate service searches only leads with profiles, so it misses the ordinary intake records. Phone matching normalizes the query but not stored formatted phone values. Reproduction: (212) 555-0100 did not match 2125550100. Duplicate detection is not invoked by manual create or CSV import.

### 8. Database configuration and delivery pipeline disagree — P1

`backend/config/settings.py:111` now selects PostgreSQL unconditionally. GitHub CI still supplies DATABASE_PATH with no PostgreSQL service. Deployment scripts still require/back up SQLite, and environment templates contain no PostgreSQL settings. A SQLite backup would not protect the database actually used by this code.

Update CI, production configuration, migrations, backup and recovery together before deploying this revision.

### 9. Reasons and immutable audit history are not enforced — P1

Status methods accept empty reasons (`services/status_transitions.py:52`); reproduction: qualification succeeded with an empty body. Generic legacy decisions and admin edits bypass the new transition service. Payment status updates are direct assignments; attendance changes do not log activity.

Activity/AuditLog are ordinary mutable models, editable/deletable in admin, and cascade-delete with a profile. Read-only API endpoints do not make the stored log immutable. Most required sensitive event categories are declared but not emitted.

## Verification results

- Backend: 42 tests ran; 41 passed, one failed because the inherited SMTP_FROM differed from the test's hardcoded expected sender. This is environment-sensitive test coverage, not evidence that SMTP delivery itself failed. The focused sender test passed when rerun with the expected sender configured. Migration consistency reported no changes detected.
- Frontend: npm run check failed with 7 errors and 3 warnings. The errors are the vendor loader/page mismatch. Warnings concern nonreactive StatusBadge values and deprecated TabView slots.
- Isolated SQLite probes, using newly migrated in-memory tables rather than production data, reproduced unpaid confirmed-booking creation by a non-staff user, blank decision reasons, duplicate payment recording, excess holds, formatted-phone mismatch, full-payment transition failure, and dashboard/add-on FieldErrors. These probes verify reachable logic defects; they do not constitute a PostgreSQL concurrency test.
- Existing tests do not exercise the new API payment contract, full payment with holds, stock contention, expired hold confirmation, role boundaries or complete lifecycle. Passing individual service tests does not validate this release end to end.

## Recommended implementation order

1. Restore working intake/listing and align auth/data contracts; align PostgreSQL CI/deployment/backup configuration.
2. Backfill canonical profiles and migrate legacy invoices/bookings into a coherent lifecycle.
3. Enforce authorization and service-only financial/status writes before exposing more controls.
4. Implement concurrency-safe inventory and idempotent payment/invoice actions with audit and rollback tests.
5. Add reliable post-payment tasks, packet content and delivery history.
6. Build the profile tabs, CSV preview, workspace, communications, dashboards and filtered lists against those APIs.
7. Complete the named behavior suite and full end-to-end test before declaring v1.2 complete.
